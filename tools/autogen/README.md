# Couchbase Node.js SDK Autogen Tools

Code generation tooling that keeps the Node.js N-API layer aligned with the C++ core.

Run everything from the **repository root**.  New to the tool?  Start with
[QUICK_START.md](QUICK_START.md).  For environment setup, see [BUILDING.md](../../BUILDING.md).

## Architecture

- **`cli.py`** — entry point, using [Click](https://click.palletsprojects.com/).
- **`commands/`** — one file per command group (e.g. `bindings`).
- **`core/`** — the heavy lifting, usable as libraries:
  - `config.py` — loads and validates `config/bindings.yaml`.
  - `llvm_env.py` — locates LLVM and assembles the clang include paths.
  - `cpp_type_parser.py` — libclang traversal of the C++ core headers.
  - `binding_builder.py` — turns the parsed type model into per-template render contexts.
  - `generate_binding_files.py` — renders the templates and splices them into the regions.
  - `post_process.py` — formats the generated files and works out what really changed.
  - `validators.py` — LLVM / pip-`clang` compatibility, and the parsed-model guard.
- **`config/`** — YAML defining what is parsed and what is generated.
- **`templates/bindings/`** — Jinja2 templates, one per generated region.

Generation is two stages.  `cpp_type_parser` produces a language-neutral type model
(`tools/bindings.json`); `binding_builder` plus the templates turn that into code.  Only the
builder knows anything about C++ or TypeScript spelling — the templates iterate and
interpolate, they do not decide.  Every field-level decision (optionality, tracing, bigint
marshalling) is reduced to a `kind` the template switches on.

## Generated files

Generation writes into the `//#region <name>` blocks of existing, hand-maintained files —
nothing is generated wholesale:

| Region | File | Template |
|---|---|---|
| Autogenerated Bindings | `lib/binding.ts` | `binding_ts.jinja2` |
| Autogenerated Method Declarations | `src/connection.hpp` | `connection_hpp.jinja2` |
| Autogenerated Method Definitions | `src/connection_autogen.cpp` | `connection_autogen_cpp.jinja2` |
| Autogenerated Method Registration | `src/connection.cpp` | `connection_cpp.jinja2` |
| Autogenerated Constants | `src/constants.cpp` | `constants_cpp.jinja2` |
| Autogenerated Marshalling | `src/jstocbpp_autogen.hpp` | `jstocbpp_autogen_hpp.jinja2` |

The table lives in `config/bindings.yaml` under `renderer.outputs`; the mapping from a
template to the context that feeds it is in `core/generate_binding_files.py`.

## Configuration (`config/bindings.yaml`)

Adding a binding should mean editing this file, not the generator.

- `cxx_client` — where the C++ core checkout and its CPM cache live, plus the include paths
  contributed by vendored dependencies.
- `parser.headers` — headers handed to libclang.  A trailing `*` means "every `.hxx` in this
  directory"; `<dir>/<prefix>*` means "every `.hxx` starting with `<prefix>`".
- `parser.types` — fully-qualified types to generate for.  A trailing `*` matches any suffix.
- `parser.excluded_name_fragments` — names skipped even when they match `types`.
- `parser.templated_requests` — class templates instantiated once per template argument.
- `observability.span_only_responses` — responses that gain `cpp_core_span` even though no
  matching request declares `parent_span`.
- `renderer.custom_defined_types` — types whose marshalling is hand-written; parsed, but not
  generated for.
- `renderer.ignored_fields` / `renderer.structs_with_allowed_private_fields` — fields never
  marshalled, and the structs exempt from the trailing-underscore rule.
- `renderer.cpp_core_variants` — `std::variant` fields flattened into a `<field>_name` /
  `<field>_value` pair, since a variant cannot be discriminated from JS alone.  See
  [std::variant fields](#stdvariant-fields).
- `renderer.bigint_fields` — fields marshalled as exact `uint64` rather than through a JS
  number, with the TypeScript type to emit.
- `renderer.outputs` — the region / file / template table above.
- `validation.allow_empty_fields` — structs that are legitimately field-less.  Any other
  struct parsing to nothing aborts generation.
- `validation.required_fields` — fields a struct must have for the parse to be believable.
- `format.formatters` — the formatter for each file suffix.  Files come from
  `renderer.outputs`, so a new region is formatted without touching this list.

## `std::variant` fields

A `std::variant` arrives in JS as a plain value with nothing on it saying which alternative it
holds, so a registered variant is flattened into a pair: `<field>_name` carries the tag naming
the alternative and `<field>_value` carries the alternative itself.  The generated converter
dispatches on the tag in both directions.

```yaml
renderer:
  cpp_core_variants:
    - core_struct: couchbase::core::range_scan_create_options
      field: scan_type
      alternatives:
        - tag: range_scan
          core_struct: couchbase::core::range_scan
```

A variant is addressed by `core_struct` **and** `field`, as a pair — a field name on its own
would pull in any unrelated struct that happens to declare the same name.

The alternatives themselves are not configured; they are read out of the C++ core, and the
entry above only names the tag each one is known by.  `validators.py` reconciles the two before
anything renders, so an alternative added, removed or renamed in the core stops generation
instead of silently dropping out of the dispatch chain.  Tags are configured rather than
derived from the C++ name because hand-written `lib/` code matches on them: renaming a core
struct must not quietly rewrite the JS contract.  `std::monostate` takes no tag — it is what an
absent value marshals to, and its branch is simply never emitted.

An unregistered variant falls back to the generic converter in `src/jstocbpp_cpptypes.hpp`,
which can marshal *to* JS but throws on the way back, since it has nothing to dispatch on.
Generation therefore ends with a sweep over every marshalled field:

- a variant with at least one alternative that has its own marshaller **could** be tagged, so a
  missing entry is reported as a warning;
- a variant of primitives and `std::monostate` has nowhere to hang a tag, so the generic
  converter is the only option and the call site is annotated to record that it is deliberate.
  `numeric_range_facet`'s `min` and `max` are the only ones today.


## Usage

```bash
# generate, format, and report what changed
python -m tools.autogen bindings generate

# what would a regeneration change?  Nothing is left modified
python -m tools.autogen bindings generate --dry-run

# parse only — writes tools/bindings.json, renders nothing
python -m tools.autogen bindings generate --parse-only

# the post-processing tail on its own — format and restore; needs no LLVM
python -m tools.autogen bindings tidy

# CI gate: exit non-zero if the committed bindings are out of date
python -m tools.autogen bindings generate --check

# full option list
python -m tools.autogen bindings generate --help
```

The three common invocations are also wired up as npm scripts:

| Script | Equivalent |
|---|---|
| `npm run gen:bindings` | `python -m tools.autogen bindings generate` |
| `npm run gen:bindings:check` | `python -m tools.autogen bindings generate --check` |
| `npm run gen:bindings:tidy` | `python -m tools.autogen bindings tidy` |

They shell straight out to `python3`, so the virtualenv still has to be active.

## Post-processing (formatting & churn)

`bindings generate` renders unformatted output, so the committed files are whatever
clang-format and prettier turn that output into.  Generation therefore finishes with two extra
steps:

1. **Format** — runs the formatter configured for each file suffix under `format.formatters`.
   The file list comes from `renderer.outputs`, so nothing outside the generated set is touched.
2. **Restore unchanged** — every generated file whose only delta against `HEAD` is the
   `Generated-On` / `Content-Hash` lines is restored, so a regeneration that changes nothing
   leaves a clean `git status`.

The restore is safe by construction: a file is only restored when its content is byte-identical
to `HEAD` once those metadata lines are removed, so real changes — including hand-edits — can
never be discarded.

Opt out with `--no-format` and `--no-restore-unchanged`.  If generation and formatting were done
by hand, run the same tail on its own with `bindings tidy`.

A file that ends the run byte-identical to how it started also gets its original mtime back, so
a no-op regeneration does not invalidate the node-gyp build.

This mirrors the Python SDK's `core/post_process.py`.  Two differences, both deliberate:

- pycbc delegates formatting to `pre-commit`, which couchnode does not use.  The formatters are
  invoked directly instead, configured per file suffix.
- `restore_unchanged` reports `untouched` as its own bucket rather than folding it into
  `restored`.  A file already byte-identical to `HEAD` needs no restoring, and checking it out
  anyway would bump its mtime on every no-op run.  pycbc never hits the case, because its
  generated files always carry a `Generated-On` banner and so always differ.

Node's regions carry no banner yet — that lands as its own commit, after the byte-identical
gate has done its job.  `strip_run_metadata` is wired in ahead of it, so adding one cannot
reintroduce churn.

`--dry-run` generates and formats for real and then puts every file back, which is the only way
it can report the answer a real run would give.  Predicting instead would mean formatting a
rendered region in isolation, away from the `.clang-format` its path resolves.

`--check` is that same measurement with an exit code, for CI.  It refuses to run alongside
`--no-format` or `--parse-only`, both of which would make the answer meaningless: unformatted
output never matches what is committed, and `--parse-only` renders nothing to compare.

## Validation

The parsed model is checked before anything is rendered.  Generation stops, listing every
problem, if a struct parsed with no fields, a struct lost a field named under
`validation.required_fields`, or an enum parsed with no values.

An empty struct is an error rather than a warning because the binding it produces still
compiles — it just marshals nothing and fails at runtime.  That is exactly how a forward
declaration shadowing its own definition presented, and it went unnoticed until the binding
was exercised.  `required_fields` covers the subtler case where a struct keeps a couple of
fields and silently loses the rest.

## Debugging a struct

When a generated binding looks wrong or empty, dump what the libclang pass actually sees.
This renders nothing and writes no files:

```bash
# fully-qualified name, leaf name, or substring
python -m tools.autogen bindings inspect --type couchbase::core::operations::query_request
python -m tools.autogen bindings inspect --type query_request

# several at once, as JSON
python -m tools.autogen bindings inspect --type query_request --type analytics_request --as-json
```

`--header` selects on the header a struct was actually declared in, which every parsed struct
records; either the path relative to the C++ core root or just the file name will do.

A struct reported as `(no fields)` that should have fields means the parser mis-read the
header.  The usual cause is a change in how the C++ core declares the type — a forward
declaration ahead of the real definition, for instance, which the parser must skip.

Two structs in the C++ core are legitimately field-less:
`couchbase::core::management::eventing::function_url_no_auth` and
`couchbase::core::range_scan_cancel_result`.  Both are listed under
`validation.allow_empty_fields`; every other empty struct fails generation.

## Extensibility

To add a new generated region:

1. Add a template under `templates/bindings/`.
2. Add a `renderer.outputs` entry naming its region, file and template.
3. Add the region markers to the target file.
4. Point the template at a context builder in `core/generate_binding_files.py`.
5. If the target file has a suffix not already in `format.formatters`, add one — generation
   refuses to guess.

To add a new generation command:

1. Add a logic module under `core/` (if needed).
2. Add a command file under `commands/`.
3. Register the command group in `cli.py`.

## A note on whitespace

Templates render with `trim_blocks` and `lstrip_blocks`, so a `{% %}` tag on its own line
contributes nothing to the output and a template reads like the code it emits.  A region body
opens and closes with a blank line; where a template carries a leading or trailing blank line,
it is load-bearing.
